# The batteries

All eight are reached through `webfluid.core.ext`, which creates each instance lazily on first
attribute access and caches it in module globals. That is why every module gets the *same* object
with no wiring — and why you must never construct one yourself.

```python
from webfluid.core.ext import scheduler, db, babel, security, events, cache, mail, jwt
```

Importing one does **not** enable it. Using a battery whose `EXT_*` switch is off raises at first
use, usually `FrameworkException("<X>.expand_fluid() has not been called.")`.

---

## SQLAlchemy — `EXT_SQLALCHEMY`

### URIs carry no driver

`SQLALCHEMY_DATABASE_URI` and every entry of `SQLALCHEMY_BINDS` must be **driver-less**; the
extension derives a sync and an async URI from the scheme.

| You write          | Sync                 | Async                |
|--------------------|----------------------|----------------------|
| `sqlite:///app.db` | `sqlite`             | `sqlite+aiosqlite`   |
| `postgresql://…`   | `postgresql+psycopg` | `postgresql+psycopg` |
| `mysql://…`        | `mysql+pymysql`      | `mysql+aiomysql`     |

Anything else raises `ValueError: Unsupported database type`. Writing the driver yourself
(`postgresql+asyncpg://…`) raises `ValueError: Please do not define drivers`.

### Models

```python
# fluid/models/entry.py
from webfluid.core.ext import db
from sqlalchemy import func
from sqlalchemy.orm import Mapped, mapped_column
from datetime import datetime


class MyModel(db.Model):
    id: Mapped[int] = mapped_column(primary_key=True)
    value: Mapped[str]
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

    def __init__(self, value: str):
        self.value = value
```

`db.Model` is a `DeclarativeBase` with three additions: `__tablename__` derived via
`camel_to_snake` when unset (`MyModel` → `my_model`), `__bind_key__` calling `set_bind` through
`__init_subclass__`, and an identity `__hash__` so detached instances hash consistently.

- **Define models under `fluid/models`** (package or module) — the generated Alembic `env.py`
  imports `fluid.models` by name, and what it cannot import is missing from autogenerated revisions.
- **Give models an explicit `__init__`** taking the fields you actually set. Every framework model
  does; it keeps construction honest and relationship collections initialised.

### Executors

`db.executor()` and `db.async_executor()` are context managers yielding a thin session wrapper. The
context manager owns the transaction: commit on a clean exit, rollback on an exception.

```python
async with db.async_executor(model=MyModel) as e:
    result = await e.exec(select(MyModel).where(MyModel.id == model_id))
    return result.first()

async with db.async_executor(model=MyModel) as e:
    return await e.insert(MyModel(value), flush=True)
```

| Method                          | Notes                                                                                                        |
|---------------------------------|--------------------------------------------------------------------------------------------------------------|
| `exec(statement, scalars=True)` | `ScalarResult` by default; `scalars=False` gives the raw `Result` (needed for `count()`, tuples, `exists()`) |
| `insert(obj, flush=False)`      | `session.add`; returns `obj`. `flush=True` populates server defaults and the PK                              |
| `delete(obj, flush=False)`      |                                                                                                              |
| `flush()`                       |                                                                                                              |
| `.session`                      | The real SQLAlchemy session, for anything the wrapper does not cover                                         |

```python
db.executor(bind_key=None, model=None)          # sync,  new session
db.async_executor(bind_key=None, model=None)    # async, new session
db.ensured_executor(...)                        # reuse an open sync executor, else open one
db.ensured_async_executor(...)                  # reuse an open async executor, else open one
db.current_executor / db.current_async_executor # the active one, or RuntimeError
```

Bind resolution: `bind_key` wins, then the model's `__bind_key__`, then `"default"`.

- **Pass `model=<YourModel>` to every executor call.** It is how the extension picks the bind.
  Omitting it works only while every model lives on the default bind — and silently connects to the
  wrong database the day one does not.
- **`ensured_*` is for reusable service functions** that must work both standalone and inside a
  caller's transaction.
- `scalars=True` is right for `select(Model)` and wrong for `select(func.count(...))`.

### What survives the block

Sessions use `expire_on_commit=False`, so **columns stay readable** after the block. What does not
survive is anything requiring a query: unloaded relationships and deferred columns raise
`DetachedInstanceError` (or `InvalidRequestError` for the `lazy="raise_on_sql"` security models).
Load them inside the block with `selectinload`.

> **Mutating an object after its executor block is a silent no-op** — no session is watching, so
> nothing is flushed. Mutate inside the block, or re-open one and merge.

### Binds

```python
SQLALCHEMY_BINDS = {"analytics": "postgresql://user:pw@host/analytics"}
```

```python
class Event(db.Model):
    __bind_key__ = "analytics"
```

Each bind has its own `MetaData`, lazily created `sync_engine` / `async_engine` and
`session()` / `async_session()` context managers. `db.get_bind(key)`, `db.get_bind_for_model(Model)`
and `db.bind_keys` reach them.

`Model.set_bind(key)` attaches at runtime; it raises `FrameworkException` if the model already has a
bind. That is how `SECURITY_MODELS_DB_BIND` and `BABEL_DATABASE_BIND` work, and how an Additive puts
its models on a configured bind from `before_enable`.

### Creating tables

```python
@app.startup_hook
async def create_tables():
    bind = db.get_bind_for_model(db.Model)
    db.Model.metadata.create_all(bind.sync_engine)
```

`create_all` is a **development convenience**. For anything you deploy use `wf migrate` — and never
mix the two on one database. `SQLALCHEMY_ENGINE_OPTIONS` is passed to both `create_engine` and
`create_async_engine` for every bind, so keep it to options both accept; leave `pool_pre_ping` and
`pool_recycle` alone.

Use the async executor everywhere you are already in `async def`. The sync one exists for code that
genuinely cannot be async, Alembic migrations, and DDL. A sync executor inside an async handler
blocks the event loop — wrap it in `webfluid.utils.run_in_executor` if you must.

## Migrate — CLI only, no `EXT_` switch

Available whenever the package is installed. It builds your application instead of running it, so it
has hard structural requirements:

1. **`main.py` exposes `prepare_fluid()`** (the generated `env.py` calls it, falling back to a
   module-level `fluid`).
2. **Config lives in `fluid/config.py`** — `wf migrate init` reads the config without executing
   `main.py`, so a `SQLALCHEMY_BINDS` defined anywhere else is invisible to template selection.
3. **`additives/` exists** — the generated `env.py` scans it.

```bash
wf migrate init <app>                       # once per app
wf migrate revision <app> -a -m "message"   # -a = --autogenerate
wf migrate upgrade <app>
wf migrate downgrade <app> -r -1
```

Everything is per **app config**, not per project: `migrate/alembic_<app>.ini` and
`migrate/migrations_<app>/`. `init` refuses to overwrite an existing environment. Revision messages
are prefixed automatically with `[<app>] [<UTC timestamp>]`.

Template choice: `multi_db` when `SQLALCHEMY_BINDS` is non-empty in the resolved config, `single_db`
otherwise.

The migration environment is a manipulated one: `EXT_SQLALCHEMY` forced on; `EXT_EVENTS`,
`EXT_CACHE`, `EXT_MAIL`, `EXT_JWT`, `WF_THEMES`, `WF_TAILWIND`, `WF_PROCESSING` forced off. Notably:

- `*_FILE` keys **are** resolved, so a migration connects with the real secret.
- `EXT_BABEL` and `EXT_SECURITY` are **not** forced off, so their models appear in autogenerated
  revisions when the app config enables them.
- `[dev]` is **not** applied — use a separate app config for a development database.
- The generated `env.py` imports `fluid.models` plus the models of every Additive **enabled for this
  app**, and skips the rest.

**Always review an autogenerated revision before applying it.** Alembic does not detect column
renames (it emits drop + add, losing data), some server-default changes, or type changes it
considers equivalent. Re-run the cycle after enabling `EXT_BABEL` or `EXT_SECURITY` — both bring
models.

## Security — `EXT_SECURITY` (requires `EXT_SQLALCHEMY`)

Building blocks, not flows: registration, login, 2FA enrollment and password reset routes are yours
to write. `SECURITY_SECRET` is required in production (debug falls back to a fixed dev secret and
warns). Without `EXT_SCHEDULING` the `ExpiredToken` cleanup job never runs and that table grows
forever.

| Service                  | Responsibility                                                 |
|--------------------------|----------------------------------------------------------------|
| `security.user_service`  | Current user, route guards, predicates, bearer grants          |
| `security.hash_service`  | argon2 `hash` / `verify` and thread-pooled `ahash` / `averify` |
| `security.token_service` | CSRF, signed single-use tokens                                 |
| `security.oauth_service` | authlib-backed social login                                    |

Models in `webfluid.extensions.security.models`: `User`, `Identity`, `Role`, `Permission`,
`TOTPSecret`, `WebAuthnCredential`, `BackupCode`, `ExpiredToken`, plus the `user_roles` and
`role_permissions` association tables.

### Relationship loading

Every relationship is `lazy="raise_on_sql"` **except** `user.totp_secret` and
`user.webauthn_credentials` (`selectin`, because the 2FA gate reads them on every gated request).

> `user.roles` does not return an empty list when unloaded — it **raises**. That is deliberate: the
> gates query the association tables directly and never navigate a relationship. Load explicitly
> with `selectinload(User.roles)` when you actually need them.

### Registration and authentication

```python
from webfluid.extensions.security.utils import validate_username, validate_password


class CreateUser(BaseModel):
    username: str
    email: EmailStr
    password: str

    _validate_username = field_validator("username")(validate_username)
    _validate_password = field_validator("password")(validate_password)
```

`validate_username` enforces `^[a-zA-Z0-9_-]{3,30}$` and raises `ValueError("INVALID_USERNAME")`.
`validate_password` raises a `ValueError` carrying an `.errors` list of symbolic codes:
`MIN_LENGTH_8`, `MIN_LOWER_1`, `MIN_UPPER_1`, `MIN_DIGITS_1`, `MIN_SPECIAL_1`.

```python
psw_hash = await security.hash_service.ahash(data.password)
ok = await security.hash_service.averify(user.psw_hash, password)
```

**Use `ahash` / `averify` inside async code.** argon2 costs roughly 40 ms of pure CPU per call; the
sync pair blocks the event loop for every one of those milliseconds. The async pair runs on a
dedicated `ThreadPoolExecutor` sized by `SECURITY_HASHER_THREADS`, which also caps concurrent
logins — that is intentional.

The current user is derived from `request.session["user_id"]`. Login stores it, logout drops it. After a
successful second factor, set `request.session["2fa_verified"] = True`.

### Route guards

```python
svc = security.user_service

async def me(user = svc.current_user): ...          # User | None, no enforcement
async def home(user = svc.require_user): ...        # 401 NOT_AUTHENTICATED
async def secure(user = svc.require_2fa): ...       # + 401 TWO_FA_REQUIRED
async def admin(user = svc.require_admin): ...      # + 403 NOT_AUTHORIZED

async def a(user = svc.require_roles(["editor", "admin"])): ...        # all
async def b(user = svc.require_any_role(["editor", "moderator"])): ... # at least one
async def c(user = svc.require_permissions(["posts:write"])): ...      # all
async def d(user = svc.require_any_permission(["a", "b"])): ...        # at least one
```

The chain: `current_user` → `require_user` (+ CSRF on unsafe methods) → an unconditional
401 `EMAIL_NOT_VERIFIED` check → `require_2fa` (only if the user *has* a second factor) → the
role/permission/grant gates. Three consequences: **every** guard past `require_user`, including
`require_2fa` itself, also demands a verified email; **every** role or permission guard also
enforces authentication, CSRF, verified email and 2FA; and `require_2fa` is a no-op for a user with
no second factor at all. Bare `require_user` is the only guard that lets an unverified email through.

The user handed to your route is **detached** — the dependency expunges it and closes the session
before yielding, so an authenticated request does not hold a pool slot. Columns are present;
relationships raise.

Predicates for a user you already hold: `svc.verified_email(user)` (sync), `svc.has_2fa(user)`
(sync), `await svc.is_admin(user)`, `has_roles`, `has_any_role`, `has_permissions`,
`has_any_permission`, `check_requirement`. Every guard also has a `_fn` twin
(`svc.require_admin_fn`) — the same resolver without the `Depends` wrapper.

### CSRF and single-use tokens

Double-submit: a signed token in a cookie, the same value in the `X-CSRF-Token` header, the raw
value in the session. `csrf_protect` skips `GET`, `HEAD`, `OPTIONS`. Failures: `403 MISSING_CSRF`,
`INVALID_CSRF`, `CSRF_MISMATCH`, `TOKEN_EXPIRED`, `INVALID_TOKEN`.

```python
token = svc.generate_token({"user_id": user.id}, salt="verify-email")
data = await svc.validate_token(token, salt="verify-email")
```

`salt="csrf"` (the default) validates signature and age only. **Any other salt burns the token** —
it is recorded in `expired_tokens`, so a second call raises `403 TOKEN_EXPIRED`. Use a distinct salt
per flow so a token minted for one cannot be replayed into another.

### Bearer grants — one route, browser and machine

With `EXT_JWT` enabled:

```python
async def publish(user = svc.requirement_or_grant(
    {"requirement": "has_any_role", "roles": ["editor", "admin"]},
    "posts:write"
)): ...
```

Requirement dictionaries are `{"requirement": "<name>"}` plus `"roles"` or `"permissions"` where
needed. Valid names: `is_authenticated`, `is_admin`, `has_2fa`, `has_roles`, `has_any_role`,
`has_permissions`, `has_any_permission`. An admin passes the requirement side unconditionally.
`requirement_and_grant` demands both. Mint tokens with the user's primary key in `sub`.

`Role.requires_2fa` is a field the battery **never reads itself** — compose it into a gate of your
own. Deciding what "requires 2FA" means for your roles is policy, and policy belongs to your app.

## Babel — `EXT_BABEL` (requires `EXT_SQLALCHEMY`)

Adds two models (`I18nKey`, `I18nMessage`) — run the migration cycle after enabling.

| Sync        | Await        | Lazy             | Signature                                       |
|-------------|--------------|------------------|-------------------------------------------------|
| `gettext`   | `agettext`   | `lazy_gettext`   | `(string, **variables)`                         |
| `ngettext`  | `angettext`  | `lazy_ngettext`  | `(singular, plural, num, **variables)`          |
| `pgettext`  | `apgettext`  | `lazy_pgettext`  | `(context, string, **variables)`                |
| `npgettext` | `anpgettext` | `lazy_npgettext` | `(context, singular, plural, num, **variables)` |

Interpolation is `%`-style. `ngettext` sets `num` for you, so `'%(num)d models'` works without
passing it. The callables are installed new-style, so `_()` works in any template.

**Use `SCREAMING_SNAKE` keys, not English sentences,** for any catalog you control. There is no
`alazy_gettext` — a lazy string resolves through `__str__`, which cannot await; use `lazy_gettext`
for module-level constants and `agettext` inside async code.

### The runtime store

```python
# fluid/i18n/__init__.py
from pathlib import Path
from webfluid.extensions.babel.utils import translation_resolver

translations = translation_resolver(Path(__file__).parent, {"en": 0, "de": 1})
```

```json
// fluid/i18n/default.json
{ "HOME_TITLE": ["Home", "Startseite"], "GREETING": ["Hello %(name)s!", "Hallo %(name)s!"] }
```

`default.json` holds singular / non-plural messages. **The file stem encodes the message data**:
`pf-other.json` → `{"pf": "other"}`, `ctx-menu.json` → `{"ctx": "menu"}`, combined with `_`. Every
value is a list indexed by the locale map.

```python
babel.update_translations("messages", translations)
```

**`update_translations` must run before `fluid.mix()`** — the calls are queued and flushed by a
startup hook, and the store rejects updates once the server is up. Call it from the factory or from
an Additive's `before_enable`. `BABEL_DISABLE_AUTOUPDATE = True` makes every call a no-op and reads
whatever the database already holds.

Static `.po` fallback: `wf babel extract` / `wf babel compile`.

### Domains

```python
babel.register_domain("shop")                  # translations/ of the project
babel.register_domain("portal", package_path)  # <package_path>/translations

@babel.domain_context("shop")
async def handler(...): ...
```

Escalation order until a domain answers: the current domain → the default domain → a domain named
`__fallback__` → the framework's own (`fluid`). If none answers, the source string is returned.
`I18nKey` is unique per `(key, domain)`, so two domains can translate the same source differently.

### Locale and timezone

**Locale:** `?lang=` → `lang` cookie → `Accept-Language` (best match against
`BABEL_SUPPORTED_LOCALES`) → `BABEL_DEFAULT_LOCALE`.
**Timezone:** `tz` cookie → `X-Timezone` header → `BABEL_DEFAULT_TIMEZONE`.

Every step is treated as untrusted input: an unparseable value is skipped, not raised. Both are
resolved once per request and cached on the `FluidContext`.

```python
@babel.locale_selector
def select_locale(): ...        # always wins, called on EVERY lookup — keep it cheap

with babel.force(locale="de", timezone="Europe/Berlin"): ...
async with babel.aforce(locale="de"): ...
```

`force` / `aforce` push a `SelectorContext` that outranks a registered selector — the correct way to
render mail or a PDF in a recipient's language.

### Formatting

Nine locale-aware Jinja filters: `datetimeformat`, `dateformat`, `timeformat`, `timedeltaformat`,
`numberformat`, `decimalformat`, `currencyformat`, `percentformat`, `scientificformat`. The same
functions live in `webfluid.extensions.babel.utils`.

**Store UTC, render local**: `to_user_timezone` on the way out, `to_utc` on the way in, and
`server_default=func.now()` on timestamp columns. `format_date`'s keyword is `fmt` (it was
misspelled `ftm` before `1.0.0b2`), and `to_utc` converts to UTC before dropping the offset, reading
a naive input as user-local.

## Events — `EXT_EVENTS`

Two shapes: **events** (fire-and-forget broadcasts) and **queries** (request/response). Public
events also reach the browser through `/ws/events` (`EVENTS_CONFIGURE_SOCKET`, default on).

```python
events.create_signal(name, singleton=False, internal=False)
events.event(name, singleton=False, internal=True)      # decorator
events.trigger(event, data=None)                        # sync, fire-and-forget
async for data in events.listen(event): ...

events.query(name, singleton=True, internal=True)       # decorator
result = await events.request(query, data=None)
```

| Flag        | Meaning                                                                        |
|-------------|--------------------------------------------------------------------------------|
| `singleton` | The name may only be registered once; a second declaration raises `ValueError` |
| `internal`  | `True` = server-only. `False` = the browser may subscribe and trigger it       |

Note the asymmetric defaults: `create_signal` defaults to `internal=False` (public), `event` to
`internal=True`. Declaring a signal public and then registering a handler without `internal=False`
raises `ValueError: Event '<name>' is already registered as public`. **Pass the flag consistently on
every call for a given name.**

Handlers take **exactly one required argument**. A mismatch raises `FrameworkException` at
registration.

```python
# fluid/events/models.py
def register():
    events.create_signal("model:created", internal=False)

    @events.event("model:created", internal=False)
    async def on_created(data): ...

    @events.query("model:count")
    async def count_models(_):
        async with db.async_executor(model=MyModel) as e:
            result = await e.exec(select(func.count(MyModel.id)), scalars=False)
            return result.scalar()
```

```python
# main.py
app.startup_hook(register)
```

Registering from a startup hook (or an Additive's `before_enable`) is the recommended shape: it is
already inside the running loop, and it keeps every contract of a module in one place. A signal
declared outside a running loop before startup is queued and wired up by a startup hook; registering
a **new** event outside a running loop **after** the server is up raises `FrameworkException`,
because nothing will ever drain it.

- `trigger` is **synchronous and does not block**: it drops the payload into each listener's buffer
  and returns. There is nothing to await — if you need an answer, use a query.
- `trigger` and `request` raise `ValueError` for an unknown name, so declare before you publish.
- Handlers run inside a fresh `FluidContext` carrying `event` and `event_data`, and inheriting the
  **request of the triggering context** when there is one.
- Queries: `singleton=True` (default) means exactly one handler and `request` returns its result;
  `singleton=False` gathers all handlers and returns a **list**.

### Delivery semantics

Best-effort by design: a bounded per-listener deque sized by `EVENTS_EVENT_QUEUE_SIZE` (default 5).
A slow consumer loses its oldest events, logged as a warning. Also **in-process only** (two workers
are two independent buses), **no persistence, no replay**, and no ordering guarantee across
channels. Fine for dashboards and live notifications; wrong for anything that must not be lost — use
the database plus a query for that.

### On the client

Only **public** (`internal=False`) events cross to the browser:

```js
const events = new window.wf.ext.events.EventManager()
await events.subscribe("model:created")
events.registerHandler("model:created", (data) => { ... })
```

Introspection: `has_event`, `has_query`, `is_singleton`, `is_internal`, `broadcaster`, `handlers`.

## Cache — `EXT_CACHE`

```python
cache.set(key, value, timeout=None);  cache.get(key);  cache.delete(key);  cache.clear()
await cache.aset(...);  await cache.aget(key);  await cache.adelete(key);  await cache.aclear()
```

`get` returns `None` for a miss **and** for an expired entry.

|                         | `redis` (default)                  | `legacy`  |
|-------------------------|------------------------------------|-----------|
| Value types             | **everything comes back as `str`** | unchanged |
| Shared across processes | yes                                | **no**    |
| Survives a restart      | yes                                | no        |

**Decode on the way out**: `int(cached)` or `json.loads(cached)` is the only shape that works on
both backends. `CACHE_TYPE = legacy` is wrong the moment you run more than one worker, and wrong for
`EXT_JWT` — use redis for anything you deploy.

There is no automatic namespacing. Prefix your keys (`myapp:…`, `<additive_id>:…`) and never write
under `jwt:`. **Never call `clear()` / `aclear()` in an app that uses JWT** — it is `flushdb` and
drops the signing keys.

The read-through pattern: cache in the query, invalidate in the event that changes the data.

```python
@events.query("model:count")
async def count_models(_):
    cached = await cache.aget("model:count")
    if cached is not None: return int(cached)
    ...
    await cache.aset("model:count", total, timeout=60)
    return total


@events.event("model:created", internal=False)
async def bust_count(_):
    await cache.adelete("model:count")
```

Never cache anything you cannot reconstruct — an entry can vanish at any moment. Always pass an
explicit timeout for values that can go stale.

## Mail — `EXT_MAIL`

```python
mail.send(to, subject, body, attachments=None, from_email=None, cc=None, bcc=None, fake_async=True)
await mail.asend(to, subject, body, attachments=None, from_email=None, cc=None, bcc=None)

with mail.client() as smtp: ...              # bare, logged-in smtplib.SMTP
async with mail.async_client() as smtp: ...  # bare, logged-in aiosmtplib.SMTP
```

> **`body` is a mapping of MIME subtype → content**, not a string. `mail.send(to, subject, "hello")`
> produces a message with one part per character, because the code iterates `body.items()`. Always
> pass `{"plain": "hello"}` (and optionally `"html"`).

`attachments` entries are `{"bytes": bytes|str, "type": str, "filename": str}` where `type` is the
MIME application subtype. A missing key raises `FrameworkException("Failed to send mail: '<key>'")`.

TLS: `MAIL_USE_TLS` is implicit TLS on port 465, `MAIL_USE_STARTTLS` is a plain connect then
`STARTTLS` on port 587. They are mutually exclusive and setting both raises at startup. The shipped
defaults — port 587, `MAIL_USE_TLS = False`, `MAIL_USE_STARTTLS = True` — are the correct pair. If
your server answers with implicit TLS, set `MAIL_PORT = 465` **and** `MAIL_USE_TLS = True`
explicitly.

`expand_fluid` also raises for `MAIL_USERNAME` without `MAIL_PASSWORD` or the reverse.

### Batching

Every `send`/`asend` opens its own SMTP session by default — right for transactional mail, wrong for
a loop. Opening a client puts it in a `ClientContext` that `send`/`asend` reuse:

```python
async with mail.async_client():
    for address in recipients:
        await mail.asend(address, "Release notes", {"plain": body})
```

**Sync and async clients do not mix** — `mail.send()` inside an `async_client()` block sees a
context whose `is_async` is `True`, treats it as no context, and opens its own connection.

Prefer `asend` everywhere you can: it does not spawn a thread per message, and delivery failures
surface as exceptions you can handle instead of dying in a detached thread. Both clients narrow SMTP
failures into `FrameworkException`.

For local development: `python -m aiosmtpd -n -l localhost:1025`.

## JWT — `EXT_JWT` (requires `EXT_SCHEDULING` **and** `EXT_CACHE`)

```python
token = await jwt.aencode(payload, audience="default", expire=None)
claims = await jwt.adecode(token, audience="default")
```

`encode` adds `exp` (now + `expire` days or `JWT_EXPIRY_DAYS`), `iat`, `nbf`, `iss` (`JWT_ISSUER`)
and `aud` (`JWT_AUDIENCES.get(audience, audience)` — an unmapped name is used verbatim). The header
carries `kid`.

Key lifecycle: a startup hook and an `IntervalTrigger` every `JWT_ROTARY_INTERVAL` days mint a new
`kid`, write `jwt:<kid>` (ttl 365 days) and set `jwt:current`. Encoding always uses `jwt:current`;
decoding reads the token's `kid` and looks up that specific secret, so an older token keeps verifying
while its secret is alive.

> **Run JWT against Redis.** With `CACHE_TYPE = legacy` the store is in-process, so every restart
> mints a new key and forgets the old ones — every previously issued token stops decoding.

**Put the user's primary key in `sub`** — the security battery's bearer gates resolve the principal
from it. Use `aencode` / `adecode` inside async code; the sync pair reaches the cache through a
blocking redis client on the event loop.

Revocation is opt-in and free when unused: put a `jti` claim in the payload and `decode` checks
`jwt:revoked:<jti>` before returning. A token without a `jti` costs no cache lookup at all.

```python
await cache.aset(f"jwt:revoked:{jti}", "1", timeout=60 * 60 * 24)
```

Give the revocation entry a TTL at least as long as the token's remaining lifetime. Audiences
separate token populations minted by the same app — a token for `"api"` cannot be replayed against a
route that decodes with `"internal"`.

## Scheduling — `EXT_SCHEDULING`

The thinnest battery: not a `FluidExtension` at all, but a bare APScheduler `AsyncIOScheduler` the
framework starts on a startup hook. Everything you know about APScheduler applies unchanged.

```python
from webfluid.core.ext import scheduler
from apscheduler.triggers.interval import IntervalTrigger
from apscheduler.triggers.cron import CronTrigger

scheduler.add_job(heartbeat, IntervalTrigger(seconds=5))
scheduler.add_job(nightly, CronTrigger(hour=3))
```

Jobs may be added **before or after** the app is constructed — `add_job` on a non-running scheduler
queues the job. Both sync and async callables work.

- A scheduled job runs **without a request**, so `FluidContext.current()` raises. Use
  `try_current()`, `fluid.url_path_for()` or `BASE_URL`.
- Jobs run on the application's event loop. Wrap blocking work in `webfluid.utils.run_in_executor`.
- The scheduler is **in-process with no persistent job store**: every process that boots runs its own
  copy of every job. With two workers, every job fires twice. Scale by giving the scheduler its own
  single-instance app config, or configure a shared job store before `start()`.

`EXT_JWT` (key rotation) and `EXT_SECURITY` (the `ExpiredToken` cleanup, every 15 days) both register
jobs here.
